# 子会话上下文交互 Demo

访问：`http://127.0.0.1:5173/context-demo.html`

这个实验页用于独立验证“创建子会话时如何选择和整理上下文”。交互已经合并到主画布；实验页自身仍不会修改主画布数据。

## 两类内容严格分开

| 内容 | 产生时机 | 维护者 | 是否自动传给子节点 |
| --- | --- | --- | --- |
| 个人笔记 | 阅读和理解过程中 | 用户手写或 AI 草拟，用户可编辑 | 否 |
| 父节点背景摘要 | 点击创建子节点之后 | AI 草拟、用户确认 | 是 |
| 引用原文 | 用户进入“摘录模式”后 | 用户按字符范围拖拽，只读保真 | 是 |
| 用户疑问 | 创建子节点时 | 用户填写 | 是 |

个人笔记描述“我目前理解了什么”；分支摘要描述“下一个会话需要知道什么”。它们不应该共用同一个字段，也不应该互相覆盖。

## Demo 采用的交互逻辑

1. 普通阅读时不接管选区，浏览器原生高亮、复制、右键菜单和移动端选择手柄全部保留。
2. 用户明确点击“摘录原文”后进入拖拽摘录模式；应用借用浏览器成熟的连续文字选区完成拖动手感，松手后才把范围转换为产品摘录并清除临时选区。
3. 用户可以从任意字开始，拖到任意字结束；因此可以摘录单个词、半句话，也可以跨段、跨消息。
4. 每次松手形成一处摘录，多次拖动可以组合不连续内容；编号表示最终传入上下文的顺序。
5. 第一步通读完整父节点会话生成背景摘要；重要性不以出现频率判断，结果始终可编辑。
6. 第二步按拖拽完成顺序确认多处只读引用原文，可逐项移除或返回会话继续摘录。
7. 第三步填写用户真正的疑问，并预览“背景摘要 + 引用原文 + 用户疑问”的最终上下文。
8. Demo 的创建按钮只展示结果，不会修改真实会话树。

摘要范围固定为完整节点，因此摘录增删不会使背景摘要失效；节点会话内容发生变化时，摘要才需要重新生成或复核。

## 为什么使用独立摘录模式

浏览器原生选区适合连续复制，却无法自然表达“选择第一、三段但跳过第二段”。选区浮层还会把普通复制误解成创建分支。独立摘录模式将两种意图分开：平时仍是标准浏览器行为；进入模式后，每次原生连续拖选会被保存为一处摘录，多次拖选即可组合不连续内容。主画布按段落渲染，仅为已保存的区间增加高亮，不再为每个字创建 DOM 元素。

## 需要通过试玩验证的问题

- 摘录模式的进入、退出状态是否足够明显？
- 拖拽中的高亮反馈是否足够明确，跨消息拖拽是否符合预期？
- 引用原文保持只读是否合适，还是需要允许调整摘录顺序？
- 没有摘录时是否仍允许创建普通子会话？
- 创建完成后，父节点是否需要显示“这个子节点引用了哪些材料”的只读回溯入口？
- 当引用材料很多时，摘要生成前是否要显示预计上下文长度？

该交互已经合并到主画布；后续试玩主要用于判断是否需要摘录排序、来源回溯和上下文长度提示。
